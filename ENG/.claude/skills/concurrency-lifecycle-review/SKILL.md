# concurrency-lifecycle-review — Concurrency and Resource Lifetime Review

- Prioritize the review target and previous version for comparison designated by the user, and fill in only undesignated items from the conversation context. If no previous version is determined, treat the last commit as the previous version. Find the common ancestor (merge-base) commit of the previous version and the last commit, and treat everything that differs between that commit and the current working tree (including staged and new files) as changes. If the target is still not determined from the conversation context, target all changes; if there are no changes or it is still unclear, confirm with the user. State the review scope and unverified items.
- Apply the review perspectives in the three items below only where they apply to the review target.
- Read the target implementation (if the review target contains changes, the code before and after the changes) and related callers to identify the execution agents (threads, asynchronous tasks, processes, instances) and shared state (memory, DB, files, external services). Check together parallel execution of multiple threads possible in the code, interleaving of asynchronous tasks and callbacks within the same thread, and concurrent execution of multiple processes or instances and duplicate execution from retries. Trace who creates, passes, uses, and releases each resource, and when it is owned, borrowed, or transferred.
- Review the access order to shared state and the atomicity of compound operations, access to resources that must be handled only on a specific thread such as the UI/main thread, and reentry into the same code during callback or event handling. Check whether locks (including file, DB, and distributed locks) and wait relationships block contractual progress or termination conditions, such as through deadlock, distinguishing them from intended normal waits, and do not conclude safety from the mere presence of locks or concurrent collections.
- Check for conflicts between cancellation, initialization, or shutdown and running tasks, distinguish a cancellation request from actual task completion, and check who observes completion, failure, and exceptions. On the normal, error, cancellation, and partial-initialization-failure paths, on paths where passing a resource or transferring ownership fails, and on paths that handle a full queue or discard queue items, check cleanup responsibility and order. Review double release, use after release, and callbacks and result application that remain after shutdown.
- For each finding, present the path and line location, the execution agents and resources, the triggering conditions and execution order, and the evidence, impact, and improvement direction. Distinguish facts confirmed in the code from inferences based on execution order. If the review target contains changes, divide findings into problems introduced or worsened by this change, existing problems, and optional improvements, and present them in that order. Cite reproduction results only when they come from existing material, results provided by the user, or runs performed with the user's approval, and match the review target and conditions. If there is no such material or a match cannot be confirmed, mark reproduction as unverified and propose the logs, state, and reproduction method needed. If there are no findings, say so.
- Review read-only for the current request and provide results only as an answer. Do not create, modify, or delete files, or change the state of the running target program, Git, DB, or external services. If a build, test, or run of the target program is needed, ask the user before running it. Even with approval, do not perform runs that could create, modify, or delete files or change state outside the target program, such as a DB or external services. Make fixes separately from this review if the user requests them after the results are presented.
