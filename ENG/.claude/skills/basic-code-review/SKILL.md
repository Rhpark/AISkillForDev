# basic-code-review — Code Design Review

- Prioritize the review target, previous version, and comparison method designated by the user, and fill in only undesignated items from the conversation context. If no previous version is determined, use the last commit (HEAD).
- If a direct comparison with a designated version is requested, compare that version with the current working tree. Otherwise, for a branch-change review or when no comparison method is determined, compare the common ancestor (merge-base) of the previous version and HEAD with the current working tree. In either case, include staged and new files, and state the comparison method and baseline used.
- If this is not a Git repository, or HEAD, the designated version, or a required common ancestor cannot be verified, state why Git-based comparison is unavailable and continue reviewing the current code in the verifiable designated scope. For any before/after difference or claim that this change introduced a problem, mark it as unverified unless supported by evidence; do not arbitrarily substitute a baseline. If no target is determined, review all changes that can be verified; if changes cannot be verified, there are no changes, or the target remains unclear, ask the user for the scope or comparison information needed.
- State the review scope and unverified items, and if the review target contains changes, also state the purpose of the changes. If the purpose cannot be confirmed from evidence, state the purpose inferred from the code, marked as an inference.
- Read the target code (if the review target contains changes, the code before and after the changes) and its callers, implementations, and tests to confirm actual usage, contracts, and dependencies, and directly check any code cited as evidence for a finding.
- From the SOLID perspective, review responsibilities, the means of extension, substitutability, per-consumer contracts, and dependency direction; judge per-consumer contracts of abstract types by the interface criteria below. From the YAGNI perspective, check abstractions, extension points, and layers by whether their necessity is explained by current requirements, contracts, and usage, not by the number of implementations. Use only requirements confirmed by evidence as current requirements, and present abstractions, extension points, and layers whose necessity is explained only by a purpose inferred from the code, marked as needing confirmation.
- For interfaces (abstract types such as interfaces, abstract classes, protocols, and traits), judge whether splitting or merging is appropriate based on actual consumers' needs, responsibility, and cohesion. Splitting an interface reduces dependence on members a consumer does not use but can increase object creation and dependency injection code, so weigh both costs together.
- For each finding, present the path and line location, the problem based on actual usage and design principles, its impact, and an improvement direction that resolves the problem with the smallest change. Mark judgments with insufficient evidence as needing confirmation. If the review target contains changes, divide findings into problems introduced or worsened by this change, existing problems, and optional improvements, and present them in that order. If there are no findings, say so.
- Review read-only for the current request and provide results only as an answer. Do not create, modify, or delete files, change the state of Git or external services, or run builds or tests. Make fixes separately from this review if the user requests them after the results are presented.
