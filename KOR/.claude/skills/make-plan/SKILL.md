# make-plan — PRD·SPEC으로 PLAN 작성

## 목적과 적용 조건

이 절차는 사용자가 make-plan(`/make-plan`, `$make-plan`) 또는 PRD/SPEC을 바탕으로 한 PLAN 작성을 명시적으로 요청했을 때만 적용한다.

입력은 PRD(요구사항: 무엇을·왜)와 SPEC(기술 명세: 어떻게)이다.
- **권장 입력**: `before-plan`이 같은 세션에서 만들었거나 사용자가 지정한 `docs/agents/output/plan/{TS}/`의 PRD/SPEC
- **대체 입력**: before-plan을 거치지 않았다면, 사용자가 지정한 문서·대화 내용 중 PRD/SPEC에 해당하는 내용. 계획은 이 내용에 근거해야 한다.

PRD/SPEC의 생성·포맷은 `before-plan`이 소유한다. 이 skill은 권장 입력의 PRD/SPEC을 분기 기준(절차 3)에 따라 갱신할 수 있으나,
새 PROMPT/PRD/SPEC을 임의로 만들지 않는다.

## 입력별 처리

| 항목 | 권장 입력 | 대체 입력 |
|---|---|---|
| 질문·답변 | PROMPT에 `[make-plan 중]` 항목으로 덧붙인다 | PLAN "결정 기록"에 남긴다 |
| 답에 따른 변경, 문서와 코드의 차이 | 분기 기준대로 PRD/SPEC을 고치고 11절 체크리스트 근거도 갱신한다 | 사용자 문서는 수정하지 않고 PLAN "결정 기록"에 남긴다 |
| 답이 없는 이슈 | PLAN "미해결 이슈" | PLAN "미해결 이슈" |
| PLAN 저장 위치 | 신규 작성은 같은 `{TS}` 폴더 | 신규 작성은 `.claude/skills/before-plan/SKILL.md`의 저장 위치·타임스탬프 규칙으로 만든 새 `{TS}` 폴더(PLAN만 만든다) |

PROMPT·PRD·SPEC을 고칠 때는 `.claude/skills/before-plan/prompt_guide.md`·`.claude/skills/before-plan/prd_guide.md`·`.claude/skills/before-plan/spec_guide.md`의 규칙을 따른다.

- **권장 입력**의 PRD/SPEC이나 PROMPT의 질문·답변을 갱신하면, 기존 PRD가 있는 경우 `.claude/skills/before-plan/SKILL.md`의 "완료 조건과 답변 대기" 규칙에 따라 PRD 머리말의 상태와 미답 질문 ID를 갱신한다.
- 상태를 갱신해도 make-plan의 진행 방식은 바뀌지 않는다. 미완료 입력 처리(절차 1)와 미해결 이슈를 남기고 진행하는 절차(절차 3)는 이 skill의 절차를 따른다.
- **권장 입력**이 부분적으로 없으면, 누락 문서·사용자의 진행 선택·확인한 근거와 처리 경위를 PLAN "결정 기록"에 설명으로 남길 수 있다. 사용자 결정·확인한 사실·모델 제안을 구분하고 출처를 명시한다. 이 설명은 기존 입력의 출처와 경위를 보존하는 용도이며, PRD/SPEC의 대체 입력이나 미결정 제안을 확정 요구사항으로 만드는 근거로 쓰지 않는다. 질문·답변 원문은 PROMPT에 기록한다. PROMPT가 없을 때의 기록 보류·복구는 절차 1을 따른다.

## 절차

1. **입력 확인**
   - 사용자가 기존 PLAN의 재개·갱신을 지정하면 그 PLAN과 명시된 입력·미해결 이슈를 먼저 읽고, 입력 유형과 관계없이 해당 파일과 폴더에서 갱신한다. 참고자료로만 지정한 PLAN을 재개 대상으로 자동 간주하지 않으며, 대체 입력 문서의 원본 보호 규칙을 유지한다.
   - **권장 입력**: `{TS}` 폴더의 PROMPT·PRD·SPEC 존재 여부와, 있는 PRD·SPEC의 11절 완료 체크리스트를 확인한다. 같은 폴더에 PLAN이 있으면 그 미해결 이슈도 확인한다.
     - PROMPT가 없으면 누락과 기록 보류 상태를 알리고, 같은 `{TS}` 폴더에서 before-plan으로 복구하는 경로를 안내한다. 사용자가 복구를 선택하면 make-plan을 멈추고 before-plan의 "재개 시 확인" 규칙을 따른다. 복구 전에는 요구사항·설계에 관한 추가 질의를 보류하고, 기존 PRD/SPEC으로 근거를 확인할 수 있는 계획만 작성한다. 질문·답변의 미기록 상태와 영향받는 작업은 PLAN 미해결 이슈에 남기고, 확인 가능한 질문·답변 원문은 복구 후 PROMPT에 기록한다.
     - 체크리스트에 미완료 항목이 있거나 PRD/SPEC 파일이 없으면, before-plan이 끝나지 않은 것으로 보고 목록을 알린 뒤 before-plan을 마저 진행할지 1차 검토 후 진행할지 묻는다.
       - before-plan을 마저 진행하면 make-plan은 멈추고, 같은 `{TS}` 폴더에서 before-plan을 이어 간다. 누락 문서는 before-plan의 "재개 시 확인" 규칙으로 작성·복구한다.
       - 1차 검토 후 진행하면 위 PROMPT 누락 시 질의 보류 규칙을 지키며 아래 대체 입력과 같은 방식으로 빠진 항목을 채우되, 기록·수정은 권장 입력 규칙을 따른다. 없는 PRD/SPEC 파일은 만들지 않는다.
     - 새로 확정·변경한 요구사항을 반영할 PRD가 없으면, 답변은 PROMPT에 기록하되 PRD 보완과 영향받는 단계·후속 단계를 미해결 이슈로 남긴다. 해당 내용을 근거로 단계를 확정하거나 구현하지 않고, 기존 PRD/SPEC으로 근거를 확인할 수 있는 범위만 구체화한다. PROMPT도 없으면 위 기록 보류 규칙을 따른다.
     - PROMPT가 있고 PLAN에 남은 미해결 이슈만 있으면, 사용자가 아직 답하지 않은 질문을 다시 묻는다. SPEC 쪽 이슈는 먼저 코드로 다시 확인하고, 코드로 정할 수 없는 것만 묻는다.
   - **대체 입력**: 그 문서·내용을 1차 검토한다. `.claude/skills/before-plan/prd_guide.md`·`.claude/skills/before-plan/spec_guide.md`의 완료 기준과 대조하고, 필요하면 이해한 내용을 사용자에게 알리거나 질문한다. 목표·범위·우선순위·성공 조건 등 사용자 판단이 필요한 내용은 기존 답변을 확인한 뒤 부족한 부분만 묻는다. 현재 상태·확인 가능한 리스크의 사실과 SPEC 항목은 절차 2에서 코드·설정으로 먼저 확인하고, 추가 정보나 사용자 선택이 필요한 것만 묻는다. 현재 구현을 사용자가 원하는 정책으로 간주하지 않는다. 답이 없는 항목은 PLAN 미해결 이슈에 적은 뒤 진행한다.
   - **공통**: 입력 위치를 모르면 최신 폴더나 저장소 문서를 임의로 찾지 않고 사용자에게 묻는다. 사용자가 이미 답한 질문은 다시 묻지 않는다.
2. **코드·문서 근거 수집** — 관련 코드와 빌드·테스트 설정, 그리고 프로젝트에 있으면 코드 구조·설계 문서와 검증 규칙 문서를 읽는다. 현행 구현에 대한 사실은 파일:라인 또는 확인한 실행 결과에 근거하고, 변경 예정 설계는 PRD/SPEC의 해당 항목과 연결한다.
3. **미해결 분기**
   - `.claude/skills/before-plan/SKILL.md`의 "분기 기준"으로 처리 경로를 판단한다.
   - 기록과 수정은 "입력별 처리" 표를 따른다.
   - 답이 없으면 PLAN 미해결 이슈에 적고 계속하며, 그 이슈에 의존하는 구현 단계에는 `(미해결 이슈 의존: ISSUE-01)`처럼 이슈 ID를 붙인다.
   - 이슈별로 필요한 확인·결정과 출처, 영향받는 단계 ID를 적는다. 직접 의존하는 단계와 그 결과를 전제로 하는 후속 단계까지 확인하고, 이슈가 해소되면 관련 단계·완료 조건·검증 계획을 갱신한다.
4. **PLAN 작성** — 신규 작성은 "입력별 처리" 표의 위치에 `{TS}_PLAN.md`를 작성한다. 기존 PLAN을 갱신할 때는 먼저 읽고 바뀐 입력에 맞게 고쳐 쓴다. 대상과 순서는 PLAN 골격의 "구현 단계" 형식으로 적는다.
   - 기존 완료 표시는 실제 구현·검증 근거와 변경 영향을 확인해 유지한다. 영향받거나 근거가 불충분한 항목은 재검토 필요로 표시하며, 계획을 작성했다는 이유로 구현·검증을 완료 표시하지 않는다.
5. **검증 계획 확인** — Unit → Integration → E2E → 수동 검증 중 적용 계층의 방법·통과 기준을 적는다. 프로젝트에 빌드·타입 검사·린트 명령이 있으면 선행 검사로 함께 적는다.
   - 출발점: 권장 입력이면 SPEC 9절(검증 전략)을 출발점으로 구체화한다.
   - 기준 출처: 프로젝트 문서와 빌드·테스트 설정에서 확인한다. 프로젝트 형태상 비적용이 분명한 계층은 `해당 없음`과 사유를 적어 제시하고, 나머지 중 찾지 못한 계층만 사용자에게 확인한다.
   - 계층별 값: 명령·통과 기준, `해당 없음`과 사유, 또는 자동 검증이 적용되지만 사용자도 명령을 정하지 못하면 `미정의`와 사유.
   - 입력에 성공 조건이 없고 답도 없으면, 통과 기준은 입력의 목표·범위에서 도출해 앞에 `(제안)`을 붙이고 미해결 이슈에 적는다.
6. **제시** — PLAN과 미해결 이슈를 제시한다. 권장 입력이면 이번에 갱신한 PRD/SPEC도, 대체 입력이면 결정 기록 중 문서와 실제 코드가 다른 점도 함께 알린다.
7. **구현 경계** — 구현까지 명시적으로 요청받은 경우에만 그 범위에서 구현을 이어가고, 그 외에는 제시 후 종료한다.
   - 미해결 이슈가 있어도 기존 요구사항·확인한 근거·위임 범위에서 수행 가능한 작업은 진행한다. 사용자가 결정해야 할 미결정 사항이나 필요한 입력 근거의 누락에 의존하는 부분과 그 결과를 전제로 하는 후속 구현은 해당 결정·근거가 확보된 뒤 수행한다. 기술 선택은 기존 요구사항과 위임 범위에서 자율적으로 결정하며, 이미 확보한 답변·위임에 추가 승인을 요구하지 않는다.

## PLAN 골격

각 핵심 단계에 근거·대상·확인 가능한 완료 조건을 연결한다. 선행 관계와 미해결 의존은 실제로 있을 때만 적고, 작업 설명에서 명확한 정보는 별도 필드로 반복하지 않아도 된다.
근거는 PRD 요구사항 ID·SPEC 절/항목 또는 대체 입력의 문서 위치·사용자 발언 위치를 참조한다. SPEC의 상세 설계는 해당 위치를 참조한다.
완료 조건은 입력과 확인한 프로젝트 검증 기준에서 구체화하며, 새 요구사항·정책을 임의로 추가하지 않는다. 성공 조건이 없는 경우의 제안은 절차 5를 따른다.

```md
# <TS> PLAN

## 입력
- 권장 입력: 실제 사용한 PRD/SPEC 경로(누락 문서는 미작성/누락 상태 명시) / 대체 입력: 근거 문서 경로, 또는 근거가 된 대화 내용의 요약

## 구현 단계
- [ ] S1. 작업 설명
      근거: PRD/SPEC의 해당 ID·절·항목 또는 대체 입력의 근거 위치
      대상: 기존 파일은 `파일:라인`, 신규 파일은 `경로 (신규)`
      선행: 선행 단계 ID (의존 관계가 있을 때)
      완료 조건: 입력·프로젝트 기준에 근거한 확인 가능한 결과
      미해결 의존: (미해결 이슈 의존: ISSUE-01) (해당 시)

## 수용기준·검증
- [ ] 선행 검사: 빌드·타입 검사·린트 명령·통과 기준(프로젝트에 있으면) 또는 해당 없음 사유
- [ ] Unit: 검증 명령·통과 기준 또는 해당 없음/미정의 사유
- [ ] Integration: 검증 명령·통과 기준 또는 해당 없음/미정의 사유
- [ ] E2E: 검증 명령·통과 기준 또는 해당 없음/미정의 사유
- [ ] 수동: 확인 절차와 통과 기준(상태값·로그·화면 등) 또는 해당 없음 사유

## 미해결 이슈
- make-plan 시점에 남은 모든 이슈(입력 문서에서 넘어온 것 포함, SPEC 10절의 리스크는 제외하고 참조만). 없으면 `없음`
- ISSUE-01: 미해결 내용 / 필요한 확인·결정 / 출처 / 영향 단계 ID

## 결정 기록
- 대체 입력: make-plan 중 질문·답변, 문서와 실제 코드가 다른 점, 그에 따라 PLAN이 문서와 달리 정한 내용. 사용자 결정·확인한 사실·모델 제안을 구분하고 출처 명시.
- 권장 입력: 부분 입력의 처리 경위를 설명할 필요가 있으면 "입력별 처리"의 설명 기록 규칙을 따른다. 질문·답변 원문은 PROMPT에 기록하며, 별도 설명이 없으면 `해당 없음 (PROMPT에 기록)`.
```

## 하지 말 것

- 특정 하네스의 `EnterPlanMode`/`ExitPlanMode`/SubAgent가 없으면 실패로 간주하지 않는다.
- 계획 작성 중 코드를 수정하지 않는다.
