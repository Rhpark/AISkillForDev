# SPEC 작성 가이드

## 역할

SPEC은 PRD(요구사항)를 **코드를 직접 탐색하며** 기술 명세로 구체화한 문서다. "어떻게" 를 다룬다.
PRD/SPEC 모두 `make-plan`에 전달되는 입력이다.

## 핵심 원칙: 코드 탐색 기반 작성

- PRD를 펴놓고, 관련 코드를 **직접 읽으며** SPEC을 작성한다 (추측으로 명세하지 않는다).
- 현행 구현·호출 관계·의존성에 대한 사실은 직접 확인한 **파일:라인 근거**를 단다. 변경 예정 설계는 PRD의 해당 요구사항 ID(기존 문서는 명확한 절·항목 참조)와 연결하고, 현행 구현과 구분해 적는다.
- 탐색 범위가 넓으면 탐색용 하위 에이전트(사용 가능한 경우)에 위임할 수 있으나, 결과는 핵심 파일을 직접 읽어 교차 검증한다.

## 작성 중 문제 발견 시 분기

- `.claude/skills/before-plan/SKILL.md`의 "분기 기준"을 따른다.
- 확신 여부와 무관하게 요구사항을 건드리면 사용자에게 확인한다.

## 완료 기준

SPEC 산출물의 `## 11. 완료 체크리스트` 항목을 모두 근거와 함께 `[x]`로 채우면 완료다.

- 근거는 현행 구현은 파일:라인, 변경 예정 설계는 PRD 요구사항, 또는 "해당 없음" 사유를 1줄 단다. 추정으로 `[x]`를 표시하지 않는다.
- 세부 내용이 있는 항목은 섹션 템플릿의 해당 절을 따른다. 산출물에서 체크리스트 항목을 임의로 추가·삭제하지 않는다.
- 9절의 대응표로 PRD의 각 요구사항이 기술 명세와 검증 시나리오·통과 기준에 연결되는지 확인한다. 이 표를 이유로 요구사항이나 성공 조건을 임의로 추가·변경하지 않는다.

## 섹션 템플릿

```md
# SPEC

## 1. 기술적 타당성
- 요구사항별 구현 가능성 검토 (신규 API 필요 여부 등)

## 2. 공개 API 정의
- 외부에 노출되는(비공개가 아닌) 신규/변경 시그니처 (함수·클래스). 없으면 "없음".
- 호출부·모듈 경계 영향 표기 (UI 바인딩 등은 해당 시 포함)

## 3. 변경/추가 대상
- {클래스/함수/파일} : 파일:라인 — 변경 내용 (신규는 경로 + (신규))

## 4. 재사용
- {기존 유틸/클래스} : 파일:라인 — 어떻게 재사용

## 5. 동작 명세 (해당 시)
- 플로우: 사용자/호출 동작 흐름
- 비즈니스 룰: 조건·정책
- 예외 처리: 오류·예외 상황과 처리 방식
- 상태 변화: 상태형 기능의 전이 (상태 있으면 필수)
- 데이터 정의: 필요한 데이터 구조

## 6. 권한 / 로깅 (해당 시)
- 필요 권한과 그 선언 위치(매니페스트·설정 파일 등)
- 로깅 지점

## 7. 영향 범위 / Breaking Change
- 코드·모듈 관점 (사용자·기능 영향은 PRD)

## 8. 환경·도구 제약
- 언어·런타임·프레임워크 버전, 빌드 구성, 관련 외부 도구 영향

## 9. 검증 전략
- Unit / Integration / E2E / 수동 검증 대상과 시나리오 (기준은 프로젝트 문서와 빌드·테스트 설정에서 확인하고, 찾지 못하면 사용자에게 확인)

| PRD 요구사항 | 기술 명세 위치 | 검증 시나리오·통과 기준 |
|---|---|---|
| REQ-01 (기존 문서는 명확한 절·항목 참조) | 해당 절·항목 | V-01: 확인 절차와 PRD 성공 조건에 따른 통과 기준 |

## 10. 리스크 / 미확인 항목
- ...

## 11. 완료 체크리스트
> 각 항목에 `[x]/[ ]`와 근거(현행 구현: 파일:라인 / 변경 예정 설계: PRD 요구사항) 또는 "해당 없음" 사유를 1줄 단다. 추정으로 `[x]`를 표시하지 않는다.
- [ ] PRD 각 요구사항이 기술 항목으로 대응됨 — 근거:
- [ ] 공개 API 정의(신규/변경 계약과 호출부 영향, 없으면 "없음") — 근거:
- [ ] 변경/추가 대상이 파일:라인으로 특정됨(신규 파일은 경로 + (신규) 표기) — 근거:
- [ ] 재사용 대상 명시(파일:라인) — 근거:
- [ ] 동작 명세(플로우/룰/예외/상태/데이터, 해당 시) — 근거:
- [ ] 권한·로깅(해당 시) — 근거:
- [ ] 영향 범위(코드·모듈)/Breaking Change 판단 — 근거:
- [ ] 환경·도구 체인 제약 확인 — 근거:
- [ ] 검증 전략(Unit/Integration/E2E/수동) — 근거:
- [ ] 현행 구현에 대한 미확인 항목과 변경 예정 설계의 미결정 항목 없음 — 근거:
```

## 하지 말 것

- 과설계 금지: 현재 요구사항·계약·사용처로 필요성이 설명되지 않는 추상화·확장 포인트를 추가하지 않는다. 상속 제한(`sealed`/`final` 등)·추상 클래스·인터페이스의 필요성은 책임·계약에 근거해 판단한다.
