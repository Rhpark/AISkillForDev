# before-plan — PROMPT·PRD·SPEC 작성

## 목적

사용자가 **before-plan** 또는 PRD/SPEC 작성을 명시적으로 요청한 경우에만 PRD/SPEC을 미리 만든다.
요구사항을 명확히 합의해야 하는 작업에 쓰며, 사용자가 명시적으로 요청했다면 작업 규모와 관계없이 진행한다.

이 스킬의 변경 대상은 지정된 PROMPT/PRD/SPEC이다. 코드·설정은 읽기 전용으로 탐색하며,
구현 작업은 사용자의 별도 요청 범위에서 처리한다.

## 산출물 (3종)

| 문서     | 역할                             | 편집 방식                                     |
|--------|----------------------------------|-------------------------------------------|
| PROMPT | 사용자와의 대화 기록 (Q&A 로그)      | **append-only** — 그대로 덧붙이기만, 요약/재해석/삭제 금지 |
| PRD    | 요구사항 정제본 (성공기준·범위·제약)   | **편집 가능** — 본문은 사용자 발언 근거 필요(현재 상태·리스크의 사실 설명은 확인한 파일:라인도 가능). 운영 정보는 PRD 가이드의 편집 규칙에 따라 갱신 |
| SPEC   | 기술 명세 (코드 탐색 기반)           | **편집 가능** — 기술적 수정은 자율, 현행 구현은 파일:라인·변경 예정 설계는 PRD 근거 필수 |

- PROMPT는 기록용이며 구현 계획의 근거로 쓰지 않는다. **PRD/SPEC만 `make-plan`의 입력**이다.

## 저장 위치 / 명명 규칙

- 폴더: `docs/agents/output/plan/{타임스탬프}/`
- 타임스탬프 형식: `yyMMdd_HHmmss` (예: `260604_121053`)
  - **셸 명령으로만 생성한다** (추측·임의 입력 금지). 예: PowerShell `Get-Date -Format "yyMMdd_HHmmss"`, bash `date +%y%m%d_%H%M%S`
  - 스킬 시작 시 1회 생성하여 3개 파일에 일관 적용. 기존 `{TS}` 폴더를 이어서 진행하라는 지정이 있으면 새로 만들지 않고 그 폴더의 기존 PROMPT/PRD/SPEC을 읽고 이어 쓴다
- 파일명: 타임스탬프 접두 — `{TS}_PROMPT.md`, `{TS}_PRD.md`, `{TS}_SPEC.md`
  - 예: `260604_121053_PROMPT.md`

## 큰 흐름

```
1. 타임스탬프 생성 + 폴더 생성 (기존 {TS} 폴더를 이어서 진행하면 생략)
2. 사용자와 대화 → PROMPT(로그)와 PRD(정제본)를 병행 기록
   - PRD 작성 전·중에 현재 동작·제약을 확인하기 위한 읽기 전용 사전 탐색을 허용한다.
     탐색 결과만으로 사용자의 목표·범위·성공 조건을 확정하거나 바꾸지 않는다.
   - 종료 게이트: PRD가 빈틈없음 (`.claude/skills/before-plan/prd_guide.md` 완료 기준 전 항목 충족)
3. PRD 기반으로 코드를 직접 탐색하며 SPEC 작성
   - 탐색 중 오류/모호 발견 시 아래 "분기 기준"에 따라 처리
4. 완료 조건 충족 시 3개 문서를 최종 저장한다 (작성 중에도 갱신할 때마다 파일에 저장한다)
5. 사용자에게 `make-plan` 실행 안내
   - 생성한 `docs/agents/output/plan/{TS}/` 경로와 PRD/SPEC 파일명을 **명시 출력**한다.
   - 이 `{TS}` 경로가 `make-plan`의 입력이며, 세션이 길어져 컨텍스트를 잃을 경우 사용자가 이 경로를 그대로 전달하면 된다고 안내한다.
```

## 질문 원칙

- 질문 전에 기존 대화·관련 문서·코드에서 답을 확인한다. 코드로 확인 가능한 사실은 먼저 탐색한다.
- 목표·범위·우선순위·성공 조건 등 사용자 판단이 필요한 내용은 질문한다. 기존 구현에서 사용자 의도를 추정하지 않는다.
- 진행을 막는 질문부터 관련 질문을 소수씩 묶어 제시한다. 선택이 필요하면 추천안과 선택에 따른 차이를 함께 제시하되, 답변 전에는 제안으로 구분한다.
- 이미 답한 질문은 전제가 바뀌거나 답변 사이에 충돌이 생긴 경우에만 이유를 밝혀 다시 묻는다.

## 분기 기준 (SPEC 작성·make-plan 진행 중 문제 발견 시)

| 상황                                          | 처리                                                    | 비고 |
|----------------------------------------------|-------------------------------------------------------| --- |
| SPEC의 현행 구현 설명만 실제 코드와 다름 (PRD 설명은 유효, 사용자 질문 불필요) | **SPEC만 수정**                                  | PROMPT/PRD 변동 없음 |
| PRD의 현재 상태·리스크에 적힌 사실이 코드와 다름 (요구사항 불변) | 확인한 근거로 **PRD의 사실 설명과 관련 SPEC 수정** | PROMPT 원문 보존 |
| 코드·문서로 해결할 수 없어 사용자에게 묻는 기술 질문 | 질문 → 답변 → PROMPT 추가 → **SPEC 수정** | PRD 변동 없음 |
| 답이 요구사항을 건드리는 질문                     | 질문 → 답변(=근거) → PROMPT 추가 + PRD 수정 → SPEC 수정 | 답변이 곧 근거 |

- 수정 경로는 위 분기표를 따른다. 요구사항 변경과 PRD의 현재 상태·리스크에 대한 사실 정정을 구분한다.
- 표의 "PRD 변동 없음"은 요구사항과 현행 사실 설명을 유지한다는 뜻이다. 운영 정보는 PRD 편집 규칙에 따라 갱신한다.
- PRD 변경은 `.claude/skills/before-plan/prd_guide.md`의 편집 규칙을 따른다.
- PRD/SPEC을 고치면 영향받는 기술 항목·검증 전략·완료 체크리스트의 근거도 재검토한다. 더 이상 충족하지 않는 항목은 `[ ]`로 되돌린다.

## 완료 조건과 답변 대기

아래 3개가 모두 충족되면 완료:
- PRD가 빈틈없음 (`.claude/skills/before-plan/prd_guide.md` 완료 기준 전 항목 충족)
- SPEC이 빈틈없음 (`.claude/skills/before-plan/spec_guide.md` 완료 기준 전 항목 충족)
- 미답 질문 없음

진행 상태는 다음 규칙으로 관리한다.

- PRD 머리말의 before-plan 상태는 같은 폴더의 문서와 질문의 최신 답변을 기준으로, 현재 before-plan 완료 조건의 충족 상태를 표시한다.
- PRD 머리말에 before-plan 전체 상태를 `진행 중` / `답변 대기` / `준비 완료`로 기록한다. `준비 완료`는 위 3개 조건을 모두 충족할 때만 쓴다.
- 필요한 답변이 없으면 질문 ID와 미답 상태를 PROMPT에 기록한다. 단계별 게이트를 지키며 답변에 의존하지 않는 작업을 진행하고, 더 진행할 수 없으면 문서를 저장한 뒤 `답변 대기` 상태·남은 질문·영향·재개 지점을 안내한다.
- 답변 대기는 **미완료**다. 미답을 임의로 해소하거나 `해당 없음`으로 처리하지 않으며, 같은 미답 질문을 반복하지 않는다.
- 미완료 문서를 완성된 make-plan 입력으로 안내하지 않는다. 사용자가 별도로 make-plan을 요청하면 해당 스킬의 미완료 입력 처리 규칙을 따른다.

## 재개 시 확인

- PRD 머리말에 마지막 완료 단계·미답 질문 ID·코드 확인 기준을 함께 남긴다. 코드 기준은 가능하면 관련 커밋과 미커밋 변경 상태를, Git을 쓰지 않으면 핵심 파일과 확인 시점을 기록한다.
- 지정된 폴더의 문서와 후속 답변을 읽고, 각 질문의 최신 답변을 기준으로 미답 여부를 판단한다. 기존 문서에 재개 정보가 없으면 확인한 범위에서 보완한다.
- 지정된 폴더에서 누락된 산출물의 작성·복구는 같은 `{TS}` 폴더에서 이 스킬과 각 가이드의 작성·편집 규칙을 따라 진행한다. PROMPT 복구에는 확인 가능한 대화 원문만 출처와 함께 기록하고, 확인할 수 없는 과거 요청·질문·답변은 누락 또는 미확인으로 명시한다. 요구사항이나 코드에서 과거 대화를 추정해 채우지 않는다. 복구했다는 이유만으로 완료 조건을 충족한 것으로 처리하지 않는다.
- 관련 코드가 달라졌는지 확인하고, 영향받는 사실·파일:라인 근거·체크 항목을 재검토한다. 코드 변경만으로 요구사항을 바꾸지 않으며, 수정 경로는 위 분기 기준을 따른다.
