# basic-code-review — 코드 설계 검토

- 사용자가 지정한 검토 대상·비교할 이전 버전·비교 방식을 우선하고, 지정되지 않은 항목만 대화 맥락으로 보완한다. 이전 버전이 정해지지 않으면 마지막 커밋(HEAD)을 이전 버전으로 본다.
- 지정 버전과의 직접 비교를 요청하면 그 버전과 현재 작업 트리를 비교한다. 그 외에 브랜치 변경분을 검토하거나 비교 방식이 정해지지 않았으면 이전 버전과 HEAD의 공통 조상(merge-base)부터 현재 작업 트리까지 비교한다. 어느 경우든 스테이징·새 파일을 포함하고, 적용한 비교 방식과 기준을 밝힌다.
- Git 저장소가 아니거나 HEAD·지정 버전·필요한 공통 조상을 확인할 수 없으면 Git 기준 비교 불가 사유를 밝히고, 확인 가능한 지정 범위의 현재 코드는 계속 검토한다. 변경 전후의 차이나 이번 변경으로 생긴 문제인지 확인하지 못하면 미확인으로 표시하며 비교 기준을 임의로 대체하지 않는다. 대상이 정해지지 않으면 확인 가능한 변경 전체를 대상으로 하되, 변경을 확인할 수 없거나 변경이 없거나 여전히 대상이 불명확하면 필요한 범위·비교 정보를 사용자에게 확인한다.
- 검토 범위·미확인 항목을 밝히고, 검토 대상에 변경이 있으면 변경 목적도 밝힌다. 근거로 변경 목적을 확인하지 못하면 코드에서 추정한 목적을 추정으로 표시해 밝힌다.
- 검토 대상 코드(검토 대상에 변경이 있으면 변경 전후 코드)와 그 호출부·구현체·테스트를 읽어 실제 사용처·계약·의존 관계를 확인하되, 발견의 근거로 인용하는 코드는 직접 확인한다.
- SOLID 관점에서 책임·확장 방식·대체 가능성·소비자별 계약·의존 방향을 검토하며, 추상 타입의 소비자별 계약은 아래 인터페이스 기준으로 판단한다. YAGNI 관점에서는 구현체 수가 아니라 현재 요구·계약·사용처로 필요성이 설명되는지를 기준으로 추상화·확장점·계층을 점검한다. 현재 요구는 근거로 확인한 요구만 쓰고, 코드에서 추정한 목적만으로 필요성이 설명되는 추상화·확장점·계층은 확인 필요로 표시해 제시한다.
- 인터페이스(interface·추상 클래스·프로토콜·트레이트 등 추상 타입)는 실제 소비자의 필요와 책임·응집도를 기준으로 분리·병합의 적절성을 판단한다. 인터페이스를 나누면 소비자가 쓰지 않는 멤버에 대한 의존은 줄지만 객체 생성·의존성 주입 코드는 늘 수 있으므로, 두 비용을 함께 따진다.
- 발견마다 경로·줄 위치, 실제 사용처와 설계 원칙에 근거한 문제, 영향, 가장 작은 수정으로 문제를 해소하는 개선 방향을 제시한다. 근거가 부족한 판단은 확인 필요로 표시한다. 검토 대상에 변경이 있으면 이번 변경으로 생기거나 악화된 문제, 기존 문제, 선택적 개선으로 나눠 이 순서로 제시한다. 발견이 없으면 없다고 밝힌다.
- 현재 요청은 읽기 전용으로 검토하고 결과를 답변으로만 제공한다. 파일을 생성·수정·삭제하거나 Git·외부 서비스의 상태를 변경하지 않으며, 빌드·테스트를 실행하지 않는다. 수정은 결과를 제시한 뒤 사용자가 요청하면 이 검토와 별도로 진행한다.
