# concurrency-lifecycle-review — 동시성·자원 수명 검토

- 사용자가 지정한 검토 대상·비교할 이전 버전·비교 방식을 우선하고, 지정되지 않은 항목만 대화 맥락으로 보완한다. 이전 버전이 정해지지 않으면 마지막 커밋(HEAD)을 이전 버전으로 본다.
- 지정 버전과의 직접 비교를 요청하면 그 버전과 현재 작업 트리를 비교한다. 그 외에 브랜치 변경분을 검토하거나 비교 방식이 정해지지 않았으면 이전 버전과 HEAD의 공통 조상(merge-base)부터 현재 작업 트리까지 비교한다. 어느 경우든 스테이징·새 파일을 포함하고, 적용한 비교 방식과 기준을 밝힌다.
- Git 저장소가 아니거나 HEAD·지정 버전·필요한 공통 조상을 확인할 수 없으면 Git 기준 비교 불가 사유를 밝히고, 확인 가능한 지정 범위의 현재 코드는 계속 검토한다. 변경 전후의 차이나 이번 변경으로 생긴 문제인지 확인하지 못하면 미확인으로 표시하며 비교 기준을 임의로 대체하지 않는다. 대상이 정해지지 않으면 확인 가능한 변경 전체를 대상으로 하되, 변경을 확인할 수 없거나 변경이 없거나 여전히 대상이 불명확하면 필요한 범위·비교 정보를 사용자에게 확인한다.
- 검토 범위와 미확인 항목을 밝힌다.
- 아래 세 항목의 점검 관점은 검토 대상에 해당하는 것만 적용한다.
- 검토 대상의 구현(검토 대상에 변경이 있으면 변경 전후 코드)과 관련 호출부를 읽어 실행 주체(스레드·비동기 작업·프로세스·인스턴스)와 공유 상태(메모리·DB·파일·외부 서비스)를 확인한다. 코드에서 가능한 여러 스레드의 병렬 실행, 같은 스레드 내 비동기 작업·콜백의 교차 진행, 여러 프로세스·인스턴스의 동시 실행과 재시도에 따른 중복 실행을 함께 확인한다. 자원의 생성·전달·사용·해제 주체와 소유·대여·소유권 이전 시점을 추적한다.
- 공유 상태의 접근 순서와 복합 연산의 원자성, UI·메인 스레드처럼 특정 스레드에서만 다뤄야 하는 자원의 접근, 콜백·이벤트 처리 중 같은 코드의 재진입을 검토한다. 잠금(파일·DB·분산 락 포함)·대기 관계가 교착 등으로 계약상 진행·종료 조건을 막는지 확인하고, 의도된 정상 대기와 구분하며, 락·동시성 컬렉션의 유무만으로 안전성을 단정하지 않는다.
- 취소·초기화·종료와 실행 중인 작업의 충돌을 확인하고, 취소 요청과 실제 작업 완료를 구분하며, 완료·실패·예외를 누가 관찰하는지 확인한다. 정상·오류·취소·부분 초기화 실패 경로와 자원 전달 또는 소유권 이전이 실패한 경로, 큐가 가득 찼을 때의 처리·큐 항목 폐기 경로에서 정리 책임과 순서를 확인한다. 중복 해제·해제 후 사용·종료 뒤 남는 콜백과 결과 반영을 검토한다.
- 발견마다 경로·줄 위치, 실행 주체·자원, 발생 조건·실행 순서, 근거·영향·개선 방향을 제시한다. 코드에서 확인한 사실과 실행 순서에 따른 추론을 구분한다. 검토 대상에 변경이 있으면 이번 변경으로 생기거나 악화된 문제, 기존 문제, 선택적 개선으로 나눠 이 순서로 제시한다. 재현 결과는 기존 자료, 사용자 제공 결과, 사용자 승인을 받아 실행한 결과 중 검토 대상과 조건이 맞는 경우에만 인용한다. 자료가 없거나 일치 여부를 확인하지 못하면 재현 여부를 미확인으로 표시하고, 필요한 로그·상태·재현 방법을 제안한다. 발견이 없으면 없다고 밝힌다.
- 현재 요청은 읽기 전용으로 검토하고 결과를 답변으로만 제공한다. 파일을 생성·수정·삭제하거나 실행 중인 대상 프로그램·Git·DB·외부 서비스의 상태를 변경하지 않는다. 빌드·테스트·대상 프로그램 실행이 필요하면 먼저 부수 효과를 확인한다. 파일을 생성·수정·삭제하거나 DB·외부 서비스 등 대상 프로그램 밖의 상태를 바꿀 수 있거나, 그 여부를 확인하지 못한 실행은 하지 않으며 이를 위한 승인도 요청하지 않는다. 이 제한에 해당하지 않는 실행에 대해서만 실행 전에 사용자에게 묻는다. 실행할 수 없으면 재현 여부·필요한 자료·재현 방법은 위 보고 규칙을 따른다. 수정은 결과를 제시한 뒤 사용자가 요청하면 이 검토와 별도로 진행한다.
